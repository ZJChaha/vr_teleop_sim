# 02 · 架构与关键设计

## 1. 三个进程内线程

```
主线程   asyncio  ── aiohttp HTTPS (静态页 index.html) + /ws WebSocket
                   └─ 只做两件事: 收手柄 JSON → 写 SharedState；收 reset 标志
                   ★ 不做几何计算, 所以网络抖动不会影响控制频率

子线程 A  MuJoCo 控制循环 500Hz
         读 SharedState (加锁拷贝) → 手柄按键状态机 → map_hand_to_target
         → ik_solve (DLS) → 写 data.ctrl → mj_step
         → 每 5 步 viewer.sync() (100Hz 刷新)

子线程 B  相机预览 (默认 20fps)
         自己的 MjModel/MjData + 自己的 GL 上下文, 只吃"qpos 快照"

子线程 C  LeRobot 数采 (50Hz, 仅采集模式)
         自己的 MjModel/MjData + Renderer, 渲染 N 路相机 → ffmpeg 管道 + parquet
```

> **双臂**时子线程 A 换成 `run_mujoco_dual`：同一条 500Hz 循环里对每条臂
> 各跑一遍"读手柄 → 映射 → IK → 下发"（`step_arms`），`mj_step` 仍然只有一次。
> 子线程 C 在双臂下不启动（这一版不采数），见 [docs/08](08_DUAL_ARM.md)。

**为什么这样切**：GL 上下文、tkinter 窗口、ffmpeg 管道都**绑线程**，
跨线程用会崩。三个线程各自独占一套 `MjModel/MjData`，通过极小的共享面通信
（一个 qpos 数组 + 一个事件队列），互不阻塞。

> 曾经踩过的坑：把 `Renderer` 建在模型 A 上、却拿模型 B 的 data 去渲染，
> 相机覆盖参数没生效，得到"遮挡 100%"的假数据。**Renderer 必须和 data 同一个 model。**

## 2. 控制链路（每次迭代）

> 链路里的**映射参数**（用哪只手、轴方向、灵敏度、是否跟姿态）全部来自
> `robot_profile.py` 的 `TeleopSpec`，见 docs/03 第 9 节。这里画的是默认值下的流程。

```
WebXR 手柄位姿 (pos, quat) ──┐
                            │  20~72Hz, 不可靠, 会抖会丢
                            ▼
                    SharedState (锁 + 最新快照 + 手部历史)
                            │
                            ▼  500Hz 主循环，每步都读
                 ┌──────────────────────────┐
                 │ 上升沿检测: 侧键按下？    │──▶ 用"当前头显朝向"重建参考系
                 └──────────────────────────┘                │
                            ▼                                │
              dp = pos - hand0_pos                           │
              dp_arm = signs * (rot_map @ dp) * scale          │  ← 坐标映射（profile 可改）
              target_tcp = tcp0 + dp_arm                      │
              dq = quat * hand0_quat⁻¹ → 目标姿态              │
                            ▼                                │
                  ik_solve(7 关节 DLS, 热启动 q_seed=上一帧解)
                            ▼
                ┌────────────────────────────────┐
                │ DRIVE_MODE = auto              │
                │  未扣扳机 → teleport (qpos ← 解)│  手感干脆
                │  扣了扳机 → servo (ctrl ← 解)   │  接触物理真实
                │  两者之间 0.12s 连续坡道过渡    │
                └────────────────────────────────┘
                            ▼
                        mj_step (500Hz)
```

### 关键数值（都实测过，改之前先读注释）

| 参数 | 值 | 为什么 |
|---|---|---|
| 仿真频率 | 500 Hz | `mj_step` 稳定性 + IK 有足够迭代机会 |
| viewer 同步 | 每 5 步（100Hz） | 用墙钟节流"降频"会把周期节拍变成相位漂移，实测掉到 31Hz 且肉眼卡 |
| IK | DLS，λ=0.005，最多 20 次/调用，外层热启动 | 单次 20 迭代**不收敛是正常的**，靠上一帧解做种子反复调用 |
| 单帧关节限幅 | **没有** | 加了就等于给指令加速度上限，实测跟踪误差 0.01mm → 51mm |
| 夹爪归一化 | `[0,1]`，0=全开 1=全闭 | 数据集统一口径，换夹爪只改映射 |

## 3. WebSocket 协议

客户端 → 服务端，文本帧 JSON：

```jsonc
// 每帧手柄状态（20~72Hz）
{
  "right": {"pos": [x, y, z],        // 已按头显朝向校准过的位置（米）
            "quat": [x, y, z, w],    // 已校准的姿态
            "trigger": 0.0,          // 0~1
            "squeeze": 0.0},         // 0~1（侧键）
  "left":  {"trigger": 0.0, "squeeze": 0.0, "x": false, "y": false}
}

// 回位（A/B 键）
{"reset": true}
```

服务端 → 客户端：**不发任何东西**。页面自己画一块"手柄立方体"（颜色随扳机变绿），
低带宽、零延迟耦合。

> 设计取舍：不做视频回传。头显里看到的是**手柄相对运动提示**，不是机械臂画面。
> 需要看画面时看电脑上的 MuJoCo viewer / 相机窗口。

## 4. IK 细节（`ik_solve`）

```python
误差 e = (target_tcp + TCP_OFF * site_z) - site_xpos      # 位置
        + 姿态误差（四元数 log 映射到 3 维）
J  = mj_jacSite(...)                                      # 6×nv
dq = Jᵀ (J Jᵀ + λ²I)⁻¹ e                                  # DLS
q  = q + clip(dq, ±IK_MAX_DQ)                             # 单次迭代步长
```

三个必须知道的点：

1. **工具点不是 site 本身**。`TCP = site_xpos - TCP_OFF * site_z`。
   参考模型里 `pinch` site 在两指垫**外面 3~4cm**，直接拿它当抓取中心，
   物体对准了指尖却停在物体上方 → 抓空。
2. **必须热启动**。每帧用上一帧的解作种子；冷启动（从 home 开始）在远离工作区时
   会掉进局部极小，表现为"够不到"。
3. **不要加单帧限幅**。真机的速度上限来自力矩，仿真里同理。人为限幅会让
   指令永远落后实际位置。

## 5. 抓取：两种模式，一行切换

`GRASP_MODE`（`server.py`）：

| 模式 | 做法 | 手感 | 数据质量 |
|---|---|---|---|
| `"physics"`（默认） | 纯物理摩擦，夹爪真夹 | 接触时切伺服，快速运动有 ~25mm 跟随误差 | ✅ 接触力真实，可训 VLA |
| `"attach"` | 扳机过阈值且物体在夹爪附近 → 吸附，搬运时锁相对位姿 | 全程 teleport，很跟手 | ❌ 接触力恒为 0，**不要用来训 VLA** |

`attach` 保留是为了对比调试和"只想验证运动学"的场景。

## 6. 为什么"不能用 kp 硬顶"

参考模型（MJCF 的 position 执行器）在快速运动时 j4/j6 力矩打满 —— 那是
"出够力矩所必需的误差"，不是数值问题：

```
kp × 2  → 立刻发散（j3 跟随误差 370°）
改 dt    → 完全无效
```

所以要么瞬移（绕开执行器，但不适合接触），要么接受速度跟随误差（物理真实）。
默认的 `auto` 是两者折中：**只在真要抓的时候**才交给物理。

## 7. 物块随机摆放

`Rig.randomize_objects()`：启动时 + 每次回位时，在
`object_random_x × object_random_y` 矩形内随机（最小间距 + 避开当前 TCP）。

**区域必须整体落在可达区内**，而且这个矩形是"采得出 4 个点"的约束：
区域太扁时，4 个方块两两相距 ≥ `object_min_sep` 可能根本无解，采样器会卡死
（`tools/validate_e2e.py` 里有防死循环写法，可参考）。

## 8. 日志与可复现

每次运行写三份（`logs/run_<时间戳>.*`）：

```
.log    文本事件流（启动/回位/抓取/异常），读起来最快
.json   列定义 + 配置快照 + 源码指纹 + 结束摘要
.bin    250Hz 浮点样本（关节/指令/末端/手柄/耗时），np.fromfile 直接读
```

出问题时把这三份给"另一个 agent"，它能复原到同一状态（见 docs/07）。
